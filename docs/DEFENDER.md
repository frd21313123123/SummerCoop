# Проверка обнаружений Microsoft Defender

`Trojan:Win32/Bearfoos.A!ml` — обнаружение антивирусом. Оно отличается от
предупреждения SmartScreen об неизвестном издателе. Название само по себе
не доказывает ложное срабатывание и не раскрывает признаки классификатора.

## Что установлено 19 октября 2026

- В локальном журнале Defender, событие 1116, зафиксированы обнаружения
  `Bearfoos.A!ml` для канонического EXE и скачанной копии релиза `0.5.0.71`.
  Тип — FastPath; есть событие защиты в реальном времени при работе с файлом,
  поэтому выполнение команды удаления не является необходимым условием детекта.
- API GitHub сообщает для EXE `0.5.0.71` размер 12013056 и SHA-256
  `d0e7cd2c0a7e523f206fa4e9566cd23c1b041132592a895d1849797a95fc502c`.
  Он совпадает с сохранившимся каноническим sidecar. Повторно скачанный EXE
  Defender заблокировал до вычисления локального hash; это ограничение проверки.
- Существовавшая локальная сборка `0.5.0.66` прошла явное сканирование
  `MpCmdRun -Scan -ScanType 3 -File <EXE> -DisableRemediation`.
  Это другой бинарник, поэтому такой результат не оправдывает выпуск `0.5.0.71`.
- В проверенных сценариях сборки нет упаковщика/обфускации и шага Authenticode.
  Используются MSVC `/MT`, обычные PE-ресурсы и манифест `asInvoker`.

Из кода удалены ненужная диагностика через скрытый PowerShell с перечислением
антивирусов и самоудаление через скрытый `cmd /c ping ... & del ...`.
При удалении данных EXE остаётся для ручного удаления после закрытия окна.
Это устранение ненужных действий, а не доказательство причины Bearfoos.
Встроенные DLL и штатное самообновление сохранены; проверка SHA-256 обновления,
откат и пользовательский INI должны продолжать работать.

## Результат локальной проверки исправления

Окончательная локальная сборка `0.5.0`, SHA-256
`25b82865815a707df39f0daae89dbf517c2619c7dd9ce25ae04022c4fb020a6e`,
и обе DLL получили `clean`, код сканирования 0, на Defender
`4.18.26090.9`, движке `1.1.26090.9`, базах `1.461.102.0`.
Защита в реальном времени была включена. Отчёт с hash всех файлов:
`build/defender-tests/report.json`. Эти же базы обнаруживали релиз `0.5.0.71`.
Это подтверждает отсутствие детекта при данной проверке, но не позволяет
приписать исходное обнаружение одной конкретной строке кода.

Проверки: 28 сценариев обновления (включая замену, откат и встроенные DLL),
31 сценарий Steam, 18 сценариев changelog и набор native save tests прошли.
Дополнительно изолированная проверка удаления подтвердила сохранение EXE,
пользовательских модов и сохранений при удалении данных мода; Windows/SAC
продолжают записываться в диагностический журнал. Проверка отсутствующего
файла отклоняется скриптом и оставляет отчёт `failed`.
Канонические EXE, sidecar и копия `dist` совпадают; пользовательский INI сохранён.

Это локальная тестовая сборка, а не новый опубликованный релиз. Обычный запуск
базовой версии может выбрать более новый старый EXE через Steam или обновление.
Для распространения исправления нужен новый штатный выпуск CI по
`PUBLISHING.md`; не выдавай локальную проверку за исправление уже опубликованного
`0.5.0.71`. Номер следующего CI-запуска в исходники не подставлялся.

## Проверить конкретную сборку

В PowerShell Windows, при необходимости с правами администратора:

```powershell
./tools/test-defender.ps1 -UpdateSignatures
./tools/test-defender.ps1 -Paths 'build/verify-release/SummerCoop-Launcher.exe' -ReportPath 'build/verify-release/defender.json'
```

Скрипт использует установленный `MpCmdRun.exe`, сканирование отдельных файлов
без применения действий и записывает результат в JSON даже при ошибке.
`-DisableRemediation` действует только на эту заказную проверку: она игнорирует
исключения и не удаляет обнаруженные файлы. Защита в реальном времени остаётся
включённой и может независимо заблокировать файл; скрипт не восстанавливает
карантин и считает невозможность чтения/проверки ошибкой.

Проверяй EXE и обе DLL. Отчёт должен содержать `status=clean`, SHA-256 каждого
файла и нулевые коды сканирования. Успешный скан не заменяет проверку запуска,
установки, обновления и результата на компьютере, где произошло обнаружение.

## Если обнаружение сохраняется

1. Сохрани название угрозы, путь, время, версию EXE, SHA-256, версию баз и отчёт.
   Сверь EXE с assets того же GitHub Release; совпадение hash подтверждает
   происхождение, но само по себе не подтверждает безопасность.
2. Передай именно обнаруженный публичный файл в
   [Microsoft Security Intelligence](https://www.microsoft.com/en-us/wdsi/filesubmission)
   как Software developer / Incorrectly detected. Укажи ссылку на исходники,
   назначение распаковки DLL и помощника обновления, шаги воспроизведения.
   Не отправляй DLL игры, ключи, INI или пользовательские журналы целиком.
3. Сохрани submission ID и дождись окончательного решения. При несогласии
   используй контакт разработчика из результата анализа. Не объявляй детект
   устранённым до повторной проверки конкретной сборки.

Отправка файла не выполняется автоматически скриптом или CI. Не меняй байты,
упаковщик или имя файла ради обхода детекта; исправляй ненужное поведение и
оспаривай ошибочную классификацию у вендора. Опубликованные assets не заменяй:
исправление выпускается под новым номером по `PUBLISHING.md`.

## Подпись

Постоянная доверенная подпись Authenticode помогает установить издателя.
Для внедрения необходим сертификат/сервис подписи и защищённый доступ CI;
самоподписанный сертификат не даёт публичного доверия. Подписывай DLL перед
встраиванием, EXE после сборки, затем проверяй подпись, тестируй и генерируй
hash/пакеты из окончательных файлов. Подпись не гарантирует снятие Bearfoos;
EV также не гарантирует отсутствие предупреждений SmartScreen.
