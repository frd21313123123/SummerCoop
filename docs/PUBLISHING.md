# Публикация SummerCoop и проверка обновлений

Эту инструкцию нужно читать перед выпуском изменений. Она дополняет
[AGENTS.md](https://github.com/frd21313123123/SummerCoop/blob/main/AGENTS.md); устройство обновления описано в
[UPDATES.md](UPDATES.md). Источник актуального поведения — скрипты и workflow
в репозитории: если они изменились, обнови и эту инструкцию.

## Подготовить изменения

1. Проверь `git status`, текущую ветку и diff. Сохрани изменения пользователя.
   Для отдельной рабочей ветки используй префикс `codex/`; автоматическая
   публикация происходит после попадания изменений в `main`.
2. Добавь новый файл `docs/changelog/<дата>-<изменение>.md` по
   [формату заметок](changelog/README.md). Нужны `## ru` и `## en`, при наличии
   перевода — `## fr`. Пиши, что изменилось для игрока. Для документации явно
   укажи, что поведение игры не изменилось. Старые заметки не используй повторно.
3. Запусти проверки, относящиеся к изменению. Для правок документации достаточно
   проверки ссылок и diff; полный набор проверок выполнит CI. При правках
   лаунчера/обновления используй соответствующие `tools/test-native-updates.ps1`,
   `tools/test-native-saves.ps1`, `tools/test-steam-binding.ps1`,
   `tools/test-release-notes.ps1`.
4. Если нужен предварительный локальный пакет с изменениями мода, собирай его
   из свежих исходников через `tools/package.ps1 -RebuildMod -GamePath <путь>`.
   Один `tools/build-launcher.ps1` встраивает имеющиеся `build/*.dll` и может
   включить старый мод. Релизная сборка CI всегда использует `-RebuildMod`.

Версия мода находится в `src/Core/Model.cs`; меняй её и сетевой протокол, когда
это требуется совместимостью игровых изменений. Версия лаунчера формируется
скриптом `tools/release-version.ps1` из версии мода и `GITHUB_RUN_NUMBER`.
Например, при версии мода `0.4.8` запуск 60 выпускает `0.4.8.60` и тег
`v0.4.8.60`. Это пример, а не номер, который нужно каждый раз подставлять.
Не фиксируй сгенерированный локальной сборкой номер в `launcher/mwversion.h`.

## Запустить выпуск

После проверки diff зафиксируй нужные файлы и отправь изменения в `main`.
Push запускает [Build and Release SummerCoop](../.github/workflows/build.yml):

1. Проверки протокола, сети, установщика, интерфейса, самообновления, Steam
   и журнала изменений на Windows runner GitHub.
2. Выделение уникального номера версии и расшифровка
   `ci/msc-references.zip.aes` в `build/ci-game`.
3. Свежая компиляция `SummerCoop.dll`, `SummerCoop.Core.dll` и автономного EXE
   с `/MT`; дополнительные проверки фактической релизной сборки.
4. Генерация описания относительно предыдущего опубликованного релиза.
   Новые заметки собираются через `tools/release-notes.ps1`; если их нет,
   используются коммиты за этот период. Результат записывается в
   `build/release-notes-<версия>.md`, тело Release и сводку Actions.
5. Загрузка шести файлов в черновик, проверка серверных SHA-256 и публикация.
   До этого момента пользователям обновление не предлагается.

Закрытые зависимости уже настроены. Ключ хранится в Actions secret
`SUMMERCOOP_REFS_PASSPHRASE`; упаковкой и расшифровкой управляет
`tools/ci-references.ps1`. Не выводи ключ и не добавляй открытые DLL игры,
личные INI или локальные учётные данные в Git и release assets. Pull request
выполняет проверки без расшифровки закрытых зависимостей и без публикации.

Для отдельного нового выпуска без изменения исходников используй
**Actions → Build and Release SummerCoop → Run workflow → main**.
Если установлен и авторизован GitHub CLI, эквивалентная команда:

```powershell
gh workflow run build.yml --ref main
```

## Дождаться результата

Проверь через GitHub API, GitHub CLI или Actions, что workflow относится
к отправленному commit SHA, имеет `status=completed`, `conclusion=success`
и успешно завершил job публикации. Затем проверь сам Release:

- Тег и версия EXE совпадают с номером, выделенным этим запуском CI.
- Для стабильного выпуска `draft=false`, `prerelease=false`, он доступен
  через `releases/latest`. Тестовые версии публикуются как prerelease.
- Описание содержит актуальные изменения и русскую/английскую секции.
- Присутствуют все шесть assets:
  `SummerCoop-Launcher.exe`, `SummerCoop-Launcher.exe.sha256`,
  `SummerCoop-Launcher-<версия>.exe`, соответствующий `.exe.sha256`,
  `SummerCoop-<версия>.zip`, `SummerCoop-<версия>-source.zip`.
- У каждого файла есть `digest=sha256:...`; скачанный файл совпадает с ним
  и с заявленным размером. Sidecar `.sha256` соответствует своему EXE.

`tools/publish-release.ps1` делает проверки при публикации, но в конце задачи
нужно также проверить доступный пользователю файл из Releases. Сохрани
загрузки и отчёты внутри `build/`, чтобы в папке лаунчера не появлялись
вспомогательные файлы.

Пример проверки стабильного EXE после успешного workflow:

```powershell
$repo = 'frd21313123123/SummerCoop'
$headers = @{ 'User-Agent' = 'SummerCoop-release-check' }
$release = Invoke-RestMethod "https://api.github.com/repos/$repo/releases/latest" -Headers $headers
$version = $release.tag_name.TrimStart('v')
$directory = Join-Path $PWD ('build/verify-release-' + $version)
New-Item -ItemType Directory -Path $directory -Force | Out-Null
$assets = @($release.assets | Where-Object name -eq 'SummerCoop-Launcher.exe')
if ($assets.Count -ne 1) { throw 'Release EXE is missing or ambiguous.' }
$asset = $assets[0]
$download = Join-Path $directory 'SummerCoop-Launcher.exe'
Invoke-WebRequest $asset.browser_download_url -OutFile $download -UseBasicParsing
$hash = (Get-FileHash -LiteralPath $download -Algorithm SHA256).Hash
if ($asset.digest -ne ('sha256:' + $hash.ToLowerInvariant())) { throw 'SHA-256 mismatch.' }
if ((Get-Item -LiteralPath $download).Length -ne $asset.size) { throw 'Size mismatch.' }
if ([Diagnostics.FileVersionInfo]::GetVersionInfo($download).ProductVersion -ne $version) { throw 'Version mismatch.' }
```

Для prerelease проверяй конкретный тег через `releases/tags/<тег>` вместо
`releases/latest`. При параллельных запусках тоже проверяй тег именно своего
workflow, чтобы не принять более поздний выпуск за результат текущей задачи.

## Проверить самообновление и обновить локальный EXE

Проверки в CI уже выполняются на том же EXE, который загружается в Release.
Для проверки перехода со старой версии используй отдельную копию в `build/`:

```text
<старый EXE> /test-update-handoff "<скачанный новый EXE>" <SHA-256 нового EXE> "<файл отчёта>"
```

Этот режим заменяет именно запущенную тестовую копию и проверяет перезапуск
через `/update-probe`. Дождись отчёта, проверь итоговый hash и сохранность INI.
Настоящая пользовательская копия не должна быть площадкой для такого теста.
Существующий `tools/test-native-updates.ps1` также проверяет замену, ошибку
запуска и откат; проверка встроенных DLL в нём требует DLL именно той сборки,
с которой был скомпилирован EXE.

Для проверки changelog фактического релиза сохрани ответ API в JSON-массив
и передай его скачанному EXE:

```text
<скачанный EXE> /test-notes "<releases.json>" "<отчёт>"
```

Проверь русскую секцию и `[preview-ru]`: там должны быть пункты текущего
выпуска без Markdown-разметки и смешения языков. Обычные тесты можно запускать
с явным `-LauncherPath <скачанный EXE>`; не вызывай их без этого параметра
после установки готового релиза, иначе они могут пересобрать и заменить
канонический EXE базовой версией. Даже `build-launcher.ps1 -OutputPath ...`
обновляет каноническую папку и `dist`.

После проверки установи скачанные EXE и его `.sha256` в
`SummerCoop-Launcher/SummerCoop-Launcher.exe` и обнови резервную копию в `dist/`.
Сохрани `summercoop-launcher.ini`, при возможности сверив hash до и после.
В пользовательской папке остаются только EXE, его `.sha256` и этот INI.
Все изображения, манифест и обе DLL мода остаются встроенными в EXE.

При обычном запуске лаунчер сам исправляет свою привязку к My Summer Car
в Steam и синхронизирует известные старые копии. Для явного применения без
запуска интерфейса предусмотрен режим:

```text
SummerCoop-Launcher.exe /register-steam "<файл отчёта внутри build>"
```

Проверь отчёт, версию и hash известного старого EXE из команды Steam.
Не завершай принудительно Steam, игру или пользовательский лаунчер.
При блокировке файла используй штатный механизм обновления или дождись
его освобождения; настройки и сохранения должны остаться целыми.

## Если выпуск не удался

Открой журнал упавшего шага и исправь причину. Незавершённый черновик
можно повторно загрузить через штатный сценарий для того же коммита;
черновик другого коммита повторно не используется. Опубликованные теги,
версии и assets не перезаписывай. Для исправления опубликованного выпуска
создай новый коммит/push или новый запуск workflow с новым номером сборки.

Не подменяй релиз вручную собранным старым EXE и не публикуй частично
загруженный черновик. Если публикация ещё не завершена, сообщай фактическое
состояние; готовность подтверждается доступным Release и проверенными файлами.
